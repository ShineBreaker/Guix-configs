# corpus-harvest-fanout — 大语料并行提炼

把「一大片只读材料」变成「一批带证据的结构化记录」：语料先压缩再切片 → 每片派一个**只读提炼 worker** → 主会话汇总去重 → 分批落库/交付。

适用：多日跨平台会话回顾、上百个日志/文档的盘点、历史归档整理。不适用：要改代码的任务（那是实施型 worker，见 `worker-handoff` 的 handoff 模板）。

规模基准（实测）：14 天 × 6 个平台 ≈ 3.5MB 原始抽取 → 压缩后 1.6MB → 10~12 个读片 worker，约 5~10 分钟并行完成 → 数百条主线 / 数十张候选卡。

## 何时用

- 语料总量超过主会话能直读的量级（大概 >300KB 文本，或 >50 个文件）
- 产物需要**可溯源**（每条结论要能指回原文），而不是一句概括
- 可以按时间/文件自然切片，片与片之间无依赖

## 四步流程

### Step 1 — 抽取与压缩（主会话自己做，别让 worker 面对原始体量）

1. 抽取/收集原始语料，逐日（或逐批）落盘，记录每批体积。
2. **机械压缩**后再看：删 `[reasoning]` 段、`[tool: ...]` 占位、harness 模板消息（TodoWrite 提醒、`<task-notification>`、`<system-reminder>`、`[OUT-OF-BAND USER MESSAGE`）。这类噪声常占 **40~80%**（某单日实测 89/166 块全是同一条 TodoWrite 提醒）。压缩后一般还能保留全部真实轮次。
3. 若抽取工具已自带噪声过滤（如 agenote ≥0.1.9 的 extract），跳过第 2 步的后半段。
4. 先自己扫一遍**用户消息时间线**（一天一行），确认切片边界与当天主题；这条时间线也是后面汇总时的骨架。

### Step 2 — 切片

- 每片 ≤300KB；超了按消息边界再拆半（顶层条目之间切，别切在条目中间）。
- 体积不均时按大小配对，而不是按天数平均分（一天的 600KB 和另一天的 30KB 不等价）。
- 单文件动辄 300KB+ 时，在任务书里写死「分块读，一次 ~40KB，**禁止整文件 read**」。

### Step 3 — 派发只读提炼 worker

任务书（模板见 `templates/readonly-harvest-brief.md`）必备：

- **只读**：禁止修改任何项目文件；检索类命令只用于查重
- **输出 schema**：字段名 + 取值域 + 正文格式；要求落盘 JSON（工作目录），便于主会话直接读，不受摘要截断影响
- **证据行**：每条结论附 日期 + 来源文件 + 原文 1~2 句；无据不写，不确定标 `存疑`
- **查重指令**：让 worker 自己跑现有检索命令（如 `agenote search "<关键词>"`），命中就写 `已有: <ID> <标题>`，不重复提议
- **只提议不落库**：保持单一写入口（主会话）
- **数量上限**（如「≤4 张最高价值」）：不设上限必收回一堆流水账
- 语言/口径要求（如「全程简体中文」「宽口径技术域而非子库名」）

并行上限按平台配额来（本机 `delegation.max_concurrent_children` 实测 10）。

### Step 4 — 汇总、去重、分批落库

1. **读落盘 JSON，不依赖摘要**：摘要会被截断，中段常含「存疑/丢弃候选/取舍理由」。
2. 合并各片候选，按标题/语义对现有库做一次总查重（用索引或检索命令），把与已有条目重叠的剔除。
3. **分批**：单轮写库有配额（如策展类「单轮新增 >10 张即暂停」）时，先写最高价值的一批，把剩余候选连同来源列给用户裁决——别默默写满。
4. 写库脚本三条纪律：
   - **幂等**：先取现有标题集合，命中即 skip（脚本中途崩了重跑不会写重复）
   - **按 ID 映射配对**，不要指望两个列表的排序一致（排序口径不同会让批量补字段整体串位）
   - 写完立刻**逐条读回/grep 验证**，尤其是自动挂链、自动补字段这类步骤
5. 提交拆两个：**上轮遗留的未提交产物**一个 commit，**本轮新产物**一个 commit，历史才可读。

## 已知坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| worker 字段类型不稳定 | 同一 `evidence` 字段有时 str 有时 list，消费端 `.strip()` 直接崩 | 消费端 `str()` 兜底 |
| 自动挂链退化 | 按文本相似度批量挂链，42 条里 38 条挂到不相关的少数高被引条目（双向写入，噪音翻倍） | 先按类别限定候选再挂本类别 hub；挂完 grep 复核 |
| 追加语义误判 | 批量补字段用的 CLI「追加」类参数多为「插到章节标题后」或「追加到文件末尾」，不是替换；连续追加会倒序堆叠 | 要改已写内容就整段重写，或按 ID 定位修文件 |
| 抽取文件体积不降反升 | 某些记忆型数据源按日重复导出整份快照（同一份 117 条 × 14 天） | 识别后单独处理（去重/跳过），别让 worker 重复读 |
| 语义相近但已覆盖 | worker 的查重只搜关键词，会漏掉同义条目 | 主会话汇总时再做一次语义级查重 |

## 收尾

- 报告形态：条数统计（抽取/候选/落库/跳过）+ 按线索分组 + 存疑清单 + 待用户决策项。
- 需要重启/重载才生效的部署（服务重启、profile 切换、网关重启）**不代跑**，给出确切命令交用户执行。
- 产出的方法论（流程本身的改进）值得回写进本 skill 的 `references/`。
