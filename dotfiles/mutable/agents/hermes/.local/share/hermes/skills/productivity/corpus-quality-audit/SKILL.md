# 语料质量审核（判定 API 驱动）

对本地语料（知识库卡片、文档、issue backlog）做全量质量判定，再把判定结果转成可执行的处置批次。判定引擎是 TypeSafe SystemOne 的 `evaluateJev`（Jev）：按问题类型返回 0~2 连续置信度，可在代码里组合成判断。

## When to Use

- 审核 / 盘点 / 治理一批卡片、笔记、知识库、backlog 的质量
- 要在成百上千条目上批量做 keep / fix / archive / merge 决策
- 需要在本地语料上跑 LLM 判定并把判定转成可执行处置
- 单条目的语义级、无法用规则判定

## 硬规则

1. **判定输出不是事实**。放量前必须校准 + 交叉验证，两步都过了才动数据。
2. **置信度分层执行**。action / defect 置信度低于约 0.4 的批次单独列出交人工，不自动执行。
3. **精度限制写进报告**。Jev 主训练语言是英文；CJK 语料绝对精度受限，相对排序与分类一致性经交叉验证后才可用。被截断的长条目注明条数。
4. **私有 schema 先读权威源**。字段合法值、序列化口径、字段间约束一律从工具源码或 CLI 输出拿，不凭经验设定——猜错的规则会在批量写时成倍放大。
5. **单组试点再放量**。任何批量写操作（合并、改属性、归档）先在 1 组端到端跑通并验证落盘，再放量。
6. **不确定就停**。边界没看清时限定表述，不拍胸脯。
7. **不为指标扭曲语义**。阈值超了只说明分布，不说明条目分错了类。判定模型的改判建议若与语义定义冲突，宁可不改并在报告里写明理由——按指标硬改会把错误固化成「已验证」。

## 流程

```text
定位通路 → 探针 → 提取语料 → 校准 → 全量判定 → 交叉验证 → 分层执行 → 收敛复检 → 报告
```

### 1. 定位判定通路

- 不要假设有独立 CLI。先 `which <judge>`；没有就在本机依赖树里找 SDK（常躺在别的工具的 `node_modules` 下），直接 import 它的客户端模块。
- **请求构造陷阱与 question 设计见 `references/judgment-api-integration.md`，本步必读。**

### 2. 探针

用最小样本（1~8 条）跑通一次完整请求，记录 token 用量与耗时，再写主管线。不要一上来就写几百行的批量脚本。

### 3. 提取语料

- 解析按**磁盘真实格式**写，不按理想格式。源格式的边角（缩进的属性抽屉、缺字段、混合 markdown/org 标记）会让提取器静默丢数据——丢掉的条目会以「属性全空」的姿态进入审核，污染判定和后续统计。
- 提取完做一次计数核对：总条数、字段缺失分布，与工具自身的 lint / schema 报告对得上再往下走。对不上说明提取器有 bug，先修提取器。

### 4. 校准（不放量）

挑 8~12 条**本地已知质量极性**的样本先跑：历史已归档的、明显过短的、有高复用标记的。看判定是否分得开。分辨不开就改 question——问更可判定的硬问题，不要问主观质量问题（设计要点见 references）。

### 5. 全量判定

全量跑，记录耗时 / 错误数 / token 用量。失败条目要区分「通路问题」（settings、JSON 兼容性）与「数据问题」（该条本身缺字段）：前者修管线，后者记入报告。

### 6. 交叉验证

用本地确定性事实校验判定方向，至少三条：

| 校验 | 期望 |
| --- | --- |
| 已知应归档的类别（如 deprecated） | 几乎全部落 archive |
| 已知低质量特征（如过短内容） | reusable 均值显著低于全体 |
| 空模板节 | 不拉低 reusable（拉低了说明模型判的是模板不是内容） |

不一致说明 question 或 state 有问题，回头改，不要带着疑点放量。

**校准维度与信号维度分开**。同一组问题里，若某一维在健康样本与退化样本上给出相同读数，把它标为校准维度（证明模型读对了文档类型），从排序权重里删掉、只留作 sanity check。把校准维度当排序依据，会产出一份没有信息量的榜单。判据与写法见 `references/judgment-api-integration.md`。

### 7. 分层执行

按「本地可判定程度」分三层，从最机械的做起：

1. **机械修复**：枚举漂移、缺必填字段、格式 / 派生字段不符——本地就能判定，批量修。
2. **语义执行**：分类、合并、连接——读条目确认后执行，单组试点。分类动作分两种，别混：**聚拢**处理「非正式类归入正式类」，判据是数量门禁；**重分类**处理「正式类之间的误判」，判据是语义定义（每类的判据写死，如 note=查到的知识 / workflow=做法总结 / debug=症状+根因+修复），必须逐张读卡。合并的机械口径：主卡取组内正文最长者；单事实薄卡（标题即结论、正文一段）按技术域归并；减卡优先合并不删——归档退出检索但可恢复。**先确认 CLI 的写能力边界**：缺 setter 的字段只能直接改文件，那就得自己同步全部派生物（派生字段、文件名、索引），而 `update` 类命令通常一次同步四处——读一遍 CLI 源码或参数面就知道缺哪个。
3. **交人工**：低置信度批次、需要拍板的取舍——列清单，不自动做。

**优先用官方 CLI 而非自造轮子**。合并、属性更新这类操作先读一遍 CLI 源码确认语义（是否保留正文、是否自动归档、索引是否原子更新、失败是否回滚），再决定调 CLI 还是绕开。`update` 类命令通常会自动同步属性、派生字段、文件名和索引——手改文件只改一处就会漏其余三处。

### 8. 收敛复检

每批执行后跑一次工具自身的 lint / format / reindex，看告警数是否下降。**执行动作本身会引入新的格式漂移**（追加正文、插属性行都会破坏对齐），收尾必须统一 format 一次再复检，否则会把「刚修好的」又算成问题。

### 9. 报告

写一份可复盘的报告：判定分布、缺陷分类分布、执行台账（每类数量与命令）、精度限制、**待用户拍板项**。报告与中间产物放同一个工作目录；目标仓库有 git 可回滚。

## Pitfalls

- **Jev 是判定 oracle，不是相似度匹配器**。成对相似度上它偏保守（两个明显同主题的条目可能只给 0.39），拿它做「该不该连边」会系统性漏连。相似度 / 聚类这类有确定性算法的问题用确定性规则（共享实词、同域约束、标题相似度），Jev 留给需要语义判断的质量分级与分类。
- **贴同一端的维度是校准维度，不是排序依据**。某维在所有样本上恒定给出高/低值，说明模型读懂了文档类型，也说明这批语料里没有反例——照它排序等于按常数排序。校准通过后从排序权重里删掉该维。
- **自动建边要限度数 + 滤噪声词**。按共享 token 生成关联时给每个节点设上限（约 3 条），否则一张条目挂几十个链接会稀释关联信号；共享词表必须剔除源格式的结构噪声（org 的 `done` / `file` / `nil` / `begin` / `src` 与章节名）——拿节名当关联证据会连出一堆假边。孤立率降到阈值附近就停，剩下 genuinely 孤立的单点知识放宽阈值只会匹配到噪声。
- **单点条目不要硬合并**。为凑数量把不同主题并成一条，比多几条更糟。合并的边界是「主卡标题仍能覆盖合并后内容」；标题承载检索入口的单事实条目不合。
- **「过时」信号是风险提示，不是结论**。超期未用只说明没人用，语义过时要读条目本身判断；已被新条目取代的，追加风险标注而非改状态。
- **空节 / 空字段先分辨是内容缺失还是模板噪音**。批量删模板节会让依赖该节的健康检查反噬；判据是「工具自己是否要求该节存在」。
- **放量前先估算 token 成本**：样本用量 × 条数，超预算就缩短 state 或分批。
- **判定模型的分类建议会向占比最高的类回归**。让模型在一组正式类之间重判，它的建议会系统性偏向样本里占比最高的类——常见形态是「改进去的比改出来的多得多」，跑完偏斜反而更糟。校验方法：数一下「改成各类」与「改出各类」的方向数，只进不出就是回归信号。修分布靠按语义定义逐张读卡，不靠让模型重判一遍。
- **报表指标的分母口径先确认再动手**。健康度、偏斜这类统计常把已归档 / 非活跃条目一起算进分母。按报表阈值决定动手前，自己按活跃条目算一遍——两者可能差好几个百分点，足以让「该修」变成「本来就没问题」。
- **多写入方共享同一仓库时，封装好的 commit 会吞掉别人的改动**。`git add` 范围宽于你的意图时，别人未提交的变动会进你的 commit，而 message 只描述你那一部分。收尾用 `git show <sha> --stat` 核对实际文件集；不符时用 `git notes --ref=<topic> append` 补说明，不要重写已推送的历史。
