# 新任务编排器

把一个全新项目或大型特性按阶段推进，每个阶段锚定一个已安装的 peer skill。本 skill 不亲自做各阶段的工作——它负责排序、门控和决策记录；阶段内容由加载进来的 peer skill 定义。

## 何时使用

- 用户显式点名走本流程（"开个新任务"、"走新任务流程"、"plan this feature"），或直接按名称加载本 skill。
- 适用于：绿地项目、大型特性、依赖大修、配置迁移——一切需要"调研→规划→构建→验证"多阶段推进的工作。
- 不适用于小改动和 bugfix——直接走 `tdd` / 诊断流程。

## 流程

按序推进。每个阶段：加载 peer skill → 干活 → 过门（见门控规则）→ 进入下一阶段。随进度把决策记进待办清单，会话中断后可以从某个门恢复。

1.  **定框** —— 一句话复述目标，定义成功标准，开待办清单、每阶段一项。本阶段不加载 peer。

2.  **调研**（领域完全已知时可跳过）—— 加载 `research`。派子 agent，只取一手来源（官方文档、源码、规范），结论写成仓库内的 Markdown 文件。

3.  **最佳实践调查** —— 网页搜索 + 正文提取：

    - 找成熟开源项目和官方文档怎么解决这类问题。优先级：MIT 许可、持续维护（近期提交 / 发布）、广为人知。非 MIT 候选允许，但必须标注许可及义务。
    - 存在能省掉真实工作的框架 / 库时，**直接用它**而不是重造。重建成熟包已提供的东西是缺陷，不是勤勉。
    - 产出：候选清单（名称、仓库、许可、维护信号、替代掉什么）。

4.  **许可决策** —— 从调查结果推导：项目自身许可必须与每个所选依赖兼容（GPL 依赖会强制项目条款）。默认建议项目自身用 MIT，除非依赖或用户意图另有要求。写明所选许可 + 一行理由；最终确认放在评审门，不静默通过。

5.  **领域建模** —— 加载 `domain-modeling`。建立 `CONTEXT.md` 领域术语表，让后续阶段共享词汇。

6.  **架构** —— 加载 `codebase-design`。深模块、接缝、接口先行。核心接口用它的 design-it-twice 并行子 agent 模式。

7.  **评审门（强制）** —— 加载 `grilling`。把所有悬而未决的决策**批量**成几轮提问——框架选型、许可、范围、取舍——每个问题带推荐答案。一次问完，不要挤牙膏。本阶段只在用户对计划**明确签字**后才结束。大计划走用户的评审流：计划 v1 → 派对抗性审查 → 修订 → v2 → 用户批准。

8.  **构建** —— 默认加载 `tdd`；设计问题还没定论时先加载 `prototype`。垂直切片、先红后绿、增量提交（约定式提交）。

9.  **收尾** —— 加载 `code-review`，解决或明确豁免所有发现；再加载 `retro`。会话可能就此结束时，提议一份交接文档。

## 门控规则

- 门没验证过绝不前进。决策门（第 7 步）只在用户显式确认后通过；工作门（2–6、8–9）只在产物存在且检查过后通过。
- 查事实是 agent 的活（派子 agent）；做决定是用户的。
- 用户已通过的门不再翻案——从待办清单里的门序号恢复。

## 陷阱

- 跳过第 3 步"直接开写"，会重新制造出这项调查本来要消灭的重复造轮子。
- 许可检查不是走过场：必须在代码压上不兼容依赖**之前**、候选还在时完成。
- 评审门是**唯一**向用户批量提问的地方。阶段中间零散提问会瓦解它。

## 验证

流程完成的标准：待办全清；评审门有用户明确签字记录；第 8 步结束时测试全绿；code-review 发现已解决或豁免；复盘已写。
