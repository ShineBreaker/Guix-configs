# 家目录体检与回收

## When to Use

- 用户说 HOME 一团糟、电脑失控、太多东西超出控制、"某个目录我很久不敢看了"
- 清理试过一次就没再用的软件 / agent CLI 的残留家目录
- `~/.cache` 或磁盘体积异常，要判断哪些能安全回收
- 本地仓库堆积未提交 / 未推送，要先清同步债
- 用户要求"家目录体检"，要一份能定期跑的只读报告

对「我的电脑失控了 / HOME 一团糟 / 太多东西超出我控制」这类诉求的分层处置。触发还包括：清理试过一次就没再用的软件残留、agent CLI 家目录堆积、`~/.cache` 体积异常、磁盘瘦身、"某个目录我很久不敢看了"、家目录体检。

核心立场：**先测量、后处方；报告事实、不越权判定；同步债优先于空间清理。**

## Always-on 规则

1. **先量再开方。** 第一步必跑 `df -h` 与全量 `du`。磁盘远未满（如 56%）时，病因是**可见性缺失**而非空间危机——处方从「清」改为「让人一眼看清」。此时清掉 20G 用户依然觉得失控，因为失控感来自"看不清"，不来自"占得多"。
2. **没查过引用就不建议删任何点目录。** 删除候选必须先过两关：
   - 引用关：项目 `AGENTS.md` / lockfile / toolchain pin 是否指着它（被 `rust-toolchain.toml` 锁定的 rustup 家目录删掉，系统 toolchain 替代会直接编译失败）；
   - 活跃关：看**内部最新文件 mtime**，不看目录自身 mtime——部署动作会刷新目录 mtime，把几个月没用的目录显示成"昨天还在动"。
3. **不许未经验证就宣称可回收量。** `guix gc` 前先数 generations（`ls -d /var/guix/profiles/per-user/$USER/*-link | wc -l`）；flatpak 前先对比 `repo/` 与 `app/` 体积。代数很少时 store 基本是活跃内容，包管理器镜像的差额才是历史版本。
4. **报告，不治理。** 体检脚本只输出事实与分层，不判定"该不该清"——哪些该留只有用户知道（Steam 沙箱数据、某个仍在用的 agent 家目录）。脚本越权判定，就是在制造下一次"看起来很对的误判"。
5. **删除一律 `trash-put`**，永不 `rm`；批量动手前逐项列清单给用户确认。
6. **同步债优先于一切空间清理。** 未推送的本地 commit 等于没有备份，是整套家目录里唯一"真的会丢东西"的一项，先于回收处理。
7. **问清主力再分层。** 用户点名的在用工具（agent CLI、主力软件）的家目录一律视为不可动，不要按体积或命名猜。

## 三层分流

| 层 | 判据 | 处方 |
|---|---|---|
| 可丢弃 | 一次性 agent/工具的家目录、>90 天无内部活动、无任何引用 | `trash-put`，逐项确认后批量 |
| 会自己长 | 沙箱数据、Wine 前缀、容器镜像、包管理器缓存 | **不清内容**；让它在体检里持续可见 |
| 在用但复杂 | 配置仓库、当前主力工具 | 不动；只补可见性，等用户真被某处卡住再局部加注释 |

包管理器缓存（`~/.cache/{uv,npm,pnpm,pip,cargo,guix,nix,...}`）单独列一节：它是唯一一类**清了绝对安全、且会立刻再长回来**的空间。清的收益是短期的，真正收益是让人看见它在长。

## 流程

1. `df -h /home /gnu` 定性：空间危机还是可见性危机。
2. 并行 `du` 扫 HOME 顶层与已知会长胖目录；单个目录超时或权限失败要吞掉、不中断整份报告。
3. 对每个删除候选过引用关 + 活跃关（见规则 2）。
4. 扫仓库同步债：`find ~/Projects -maxdepth 3 -type d -name .git`，逐个取 `git status --porcelain | wc -l`、`git rev-list --count @{u}..HEAD`、`HEAD..@{u}`，只列非零。
5. 交付**一只读体检脚本**，而不是一串删除动作。
6. 把脚本落进配置源仓库并完成登记（本机：Guix-configs `dotfiles/immutable/utilities/.local/bin/` + `tools/toolbox` 的 `tools.yaml` + fish 补全 + 手册），保持可版本化、可回滚。

## 体检脚本要点

- 五段输出：磁盘 / HOME top 15 / 会长胖目录 / 仓库同步债 / 可回收空间 + 包管理器缓存。
- `du -sh` 一律包 `timeout`，失败留空而不退出。
- 仓库节在 `while read` 子 shell 里 `cd`，失败即跳过该仓库。
- 可回收节每个条目附一句"清了损失什么"（重下时间 / 历史版本 / 需确认）。
- 并行 `du` 用 `xargs -0 -P 4` + `export -f`，串行扫几百 G 要等几分钟。

## 踩坑

- `du -sh ~/.*` 只给顶层总量，会漏掉大目录的**内部**构成；对 `~/.cache` 这类要再钻一层 `du -sh ~/.cache/*`。
- 目录 mtime 不可信；判活跃用内部最新文件 mtime。
- 按命名猜"这是尸骸"会误伤（`~/.rustup`、`~/.minimax` 都像残留，实为锁定依赖）。
- 配置仓库源里的脚本改完先原地 `bash <源文件>` 验证，再走部署重建；部署本身可能夹带工作区里他人的未提交改动，要先告知。
- **先量自己的话再说。** 处方未经验证就输出（如"gc 能回收大头"）会被测量直接推翻；把"预估"说成"可回收"是这类任务里最贵的错。
- 别给失控的系统再加一层管理体系。用户已经因为"为了管配置而建的体系本身变复杂"而失控时，新增工具/新目录/新约定都是反向的；最小形态是一只读脚本 + 一条登记。
