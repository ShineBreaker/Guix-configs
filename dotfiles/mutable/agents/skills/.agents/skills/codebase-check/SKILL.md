# 代码库整理

编排一次代码库整理：先只读审计，用户挑选要处理的事项，再逐项执行修复并验证。

核心立场：**AI 写代码、AI 测试代码；工程师拥有判断权** —— 架构、边界、克制、以及让 AI 输出长期一致的规则。

## 何时使用

- 用户显式点名走本流程（"整理一下代码库"、"做一次架构梳理"、"走 tidy 流程"），或直接按名称加载本 skill。
- 适用于：依赖审计（已装 vs 可用替代）、死代码清扫、架构评审、AI 代码库衰败治理、任何结构化多阶段清理。
- 不适用于单个已知问题——直接修。

## 前置条件

Peer skill 已安装，加载方式 = 读取对应 SKILL.md 并遵循其流程：

| Peer skill                    | 路径                                                      |
| ----------------------------- | --------------------------------------------------------- |
| improve-codebase-architecture | `~/.agents/skills/improve-codebase-architecture/SKILL.md` |
| codebase-design               | `~/.agents/skills/codebase-design/SKILL.md`               |
| tdd / code-review             | `~/.agents/skills/<name>/SKILL.md`                        |

## 治理原则（内化自 ai-codebase-hygiene）

以下原则贯穿整个整理流程，不再依赖外部 skill：

1. **Bug 循环** —— 修 bug 时不止修本身：回归测试（必须在旧代码上失败）→ 搜索同类路径 → 把"为什么"写入模块 rules 文件。
2. **克制门控** —— 每个候选变更都要过克制检查：不新增常驻开销、不新增系统权限、有合理默认值时不新增设置、不借清理之名扩大范围。如无必要，勿增实体。
3. **Rules 文件承载决策理由** —— 测试记输入输出，rules 记边界与历史原因。按模块拆分、按需加载、随行为变化及时修剪——过时的 rules 比没有更糟。
4. **五态发布验证** —— 改动触及发布产物时，本地代码、git 提交、签名产物、线上文件、用户实际收到的是五个不同状态，需逐一确认。

## 流程

1.  **圈定范围** —— 用户一句话，或从 `git log --oneline` 热点出发；开待办清单（审计 / 挑选 / 执行 N 项 / 验证）。步骤 4 用户挑选之前保持只读：shell 查 git 历史，文件读取 / 代码搜索工具查代码，不写仓库。

2.  **审计** —— 加载 `improve-codebase-architecture` 并遵循执行（其中会进一步加载 `codebase-design` 取"深模块"词汇表；子 agent 遍历；摩擦点调查；HTML 报告写到系统临时目录，绝不写进仓库）。结束时列出候选，请用户挑选。

3.  **扩充候选池** —— 用以下治理原则清单核对每个已选 / 相邻区域：

    - **回归测试缺口**：最近修过的 bug 类是否缺回归测试？"看着对、实际错"的失败模式有没有测（迟到的过期结果、静默的进程失败、命令返回成功但应用未实际更新）？
    - **Rules 健康度**：有边界和禁改物的地方，rules 文件是否缺失或过时？
    - **范围腐化**：投机性配置、兼容分支、无用户价值的常驻开销——每个单独合理的设置是否已复合成不可维护的状态？
    - **跨产物一致性**：文档、生成物、配置之间有没有不一致？

    把这些并入候选清单，和第 2 步的候选合成**一张清单、一次决策**。顺带发现的 AI 泛滥型候选项标记 `Speculative`，对它们删除优先于新增。

4.  **用户挑选门（强制）** —— 呈现合并清单，只对显式选中的项动手。被否决但理由关键的项：提议补一条 ADR，让未来审计不再重复提出（见 improve-codebase-architecture §3）。

5.  **逐候选执行** —— 一次一项：行为变更加载 `tdd` 走红→绿；纯重构把测试随代码搬移并保持绿；提交前过 `code-review` 清单。约定式提交，一个逻辑变更一次提交。某候选膨胀到超出报告卡片范围时，停下来重新向用户确认——绝不静默扩大。

6.  **验证收尾** —— 仓库聚合检查全绿（`make verify` / 测试套件 / CI 等价物）。**绿勾不等于完事** —— 改动触及发布产物时，逐一确认五态（本地代码 / git 提交 / 签名产物 / 线上文件 / 用户实际收到）。收尾写复盘：改了什么、新增了哪些 rules 或测试。

## 门控规则

- 用户挑选前（步骤 1–4）只读；挑选后逐候选写入。
- 每个候选必须全绿（测试 + 聚合检查）才能开始下一个。
- 一切删除都要用户显式确认——审计只能说"候选"，用户说"做"才算数。

## 陷阱

- HTML 报告必须写临时目录；写进仓库就破坏了只读审计。
- 加深型重构（改接口）比看起来更险——优先选在现有接缝处有测试覆盖的候选。
- 删代码要和加代码同等严谨：先确认无调用方（代码搜索），再删，再重验证。
- 过时的 rules 文件会让审计捍卫过时的边界——先检查 rules 新鲜度，再让它否决候选。
- 人工 QA AI 输出会重新引入最慢的环节。审查判断和边界，不要逐个审查测试运行。

## 验证

- 审计阶段：临时目录存在报告文件，含至少一张候选卡（Files / Problem / Solution / Benefits）。
- 执行阶段：每个选中候选有对应提交；最终聚合检查退出码 0；触及发布产物时，五态逐一确认已记录。
- 健康度信号：`git log --oneline --grep='^fix' | wc -l`（fix 提交量）、最近 fix 是否带回归测试、rules 文件是否覆盖关键模块。
