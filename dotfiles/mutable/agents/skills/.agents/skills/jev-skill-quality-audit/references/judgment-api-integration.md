# Jev（TypeSafe SystemOne）集成要点

任何本地脚本 / CLI 直接调 `evaluateJev` 都适用。特定管道（如日报）的阈值口径不在此文件。

## 请求构造的三个陷阱

1. **settings 值域先读 validator，不要凭经验设**。`validateJevSettings` 拒绝超限值，失败一律返回 `invalid_request`，不指出是哪个字段超限——症状像通路不通。已知 `requestTimeoutMs` 上限 30000，设 90s 会让**每一个**请求失败。设值前先 grep 安装目录里的 `DEFAULTS` 与各 `integer(...)` 的 min/max。
2. **state 里的 `undefined` 会被拒**。`validateJevEvaluateInput` 要求严格 JSON，`undefined` 属性直接报 not JSON-compatible。批量场景（源数据属性大量缺失）必须递归 prune 掉 undefined 键，否则失败率恰好等于缺字段的占比——极易误判成网络或凭据问题。
3. **超长 state 自己截断**。保留头部（结论）与尾部（教训），在截断处标注，避免模型把片段当全文。token 用量从每次返回的 `usage` 累加，放量前用样本估算总成本。

## question 设计

- **问可判定的硬问题，不问主观质量**。「值得读吗 / 新信息量多少」头部与中部只差 0.2，jev 返回平滑连续置信度，没有决策边界。改问「有没有硬事实」「是不是官宣」「是否已废弃」这类有客观判据的问题。
- **score 类返回 0~2 连续值，不是离散档**。`>= 1.0` 的语义是「置信度 ≥ 50%」，不是「满分」；0.49 与 0.51 没有实质区别，别把门槛当成精确边界。
- **不设主题相关性门槛**（除非任务本身限定域）。用受众相关性做准入会把边缘但有价值的内容整批挡掉。
- **天然低分的品类要留旁路**。架构说明、踩坑记录这类内容信号天然低但有工程价值——只参与排序，不设准入门槛；确需准入的品类单独判定后绕过双保底，别让两个保底叠加把品类本身卡掉。
- **一个问题只问一件事**，组合逻辑放代码里，便于单独调某一维的阈值。
- **分类题的选项要防「主导类回归」**。让模型在一组正式类之间重判时，它的建议会系统性偏向样本里占比最高的类。校验方法：数一下「改成各类」与「改出各类」的方向数，只进不出就是回归信号——此时应改为按语义定义逐张读卡，而不是继续让模型重判。选项的 criteria 要把边界写死（每个类「算什么 / 不算什么」），否则模型按印象归类。

## 什么该问 Jev，什么该用确定性算法

| 任务 | 用什么 |
| --- | --- |
| 质量分级、分类、缺陷定性 | Jev |
| 词汇 / 结构相似度、聚类、去重候选 | 确定性算法（共享实词、同域约束、标题相似度） |
| schema 合法值、字段必填、格式合规 | 工具自身 lint |
| 计数、分布、孤立率 | 本地统计 |

Jev 在成对相似度上偏保守：两个明显同主题的条目可能只给 0.39。拿它做「该不该连边」会系统性漏连——相似度有确定性算法可解，Jev 留给需要语义判断的部分。

## 口径写进代码与报告

- 分制（0~2 连续）、每个门槛挡的是什么、为什么某个信号只排序不准入——写进 docstring。后来者最容易把「连续值」当「三档离散分」重新引入。
- 报告显式写明精度限制：Jev 主训练语言英文，CJK 内容绝对精度低于英文，但相对排序经交叉验证后可用；被截断条目注明条数。别让读数被当成精值。
