# jev 口径调整后的验证流程

改完 QUESTIONS 或入选逻辑后，必须拿**同一份历史数据**重跑对比，不能只看代码「应该对」。

## 步骤

1. 备份基线：`cp -r <state>/picked /tmp/jev-baseline`
2. 重跑且**不覆盖正式 state**：`jev_score.py score --input <state>/new/<date>.json --state-dir /tmp/jevtest`
3. 对比三个数：picked 条数、新增条目、被剔除条目
4. 逐条打印新增/剔除条目的 `is_news / has_facts / is_release / signal / worth`，按 has_facts 排序，看「想留的」和「想剔的」分数区间是否重叠

## 判据

- **被剔除的每一条都要能说出理由**。政策/娱乐/博彩/吆喝类该剔；架构说明、工具改版、踩坑记录、官宣被剔就是误杀。
- **has_facts 分不开噪音与工程内容**：实测工程类工具说明 0.07 与博彩赔率 0.11 落在同一区间。所以它只能做排序信号，不能做硬门槛——这是反复验证过的结论，不要再加回来。
- **大新闻要做反向验证**。出现重大发布时，grep 数据里的相关关键词，逐条看分数是否过线。官宣句式短促、signal/worth 天然偏低，是最容易被双保底卡掉的一类；漏掉它比多进一条噪音严重得多。
- **单一账号占比异常就是灌水信号**。统计 picked 里各 handle 的条数，某账号占比过高时用 mute 从源头切，不要靠调 jev 阈值补救。
- 阈值口径写进 docstring：分制（0~2 连续）、每个门槛挡的是什么、为什么某个信号只排序不准入。后来者最容易把「0~2 连续值」当「三档离散分」重新引入。

## 跨管道通用：直接调 evaluateJev 的集成要点

以上是日报管道的口径；以下是任何本地脚本/CLI 调 `evaluateJev` 都适用的集成规则。

### 请求构造的三个陷阱

1. **settings 值域先读 validator，不要凭经验设**。`validateJevSettings` 拒绝超限值，且失败一律返回 `invalid_request`，不指出是哪个字段超限。已知 `requestTimeoutMs` 上限 30000——想设 90s 会让**每一个**请求失败，症状像通路不通。设值前先 grep 安装目录里的 `DEFAULTS` 与各 `integer(...)` 的 min/max。
2. **state 里的 `undefined` 会被拒**。`validateJevEvaluateInput` 要求严格 JSON，`entry_type: undefined` 直接报 "not JSON-compatible"。批量场景（源数据属性大量缺失）必须递归 prune 掉 undefined 键，否则失败率恰好等于缺字段的占比——极易误判成网络或凭据问题。
3. **超长 state 自己截断**。单条正文过长时截断并保留头部（结论）与尾部（教训），在截断处标注，避免模型把片段当全文。token 用量从每次返回的 `usage` 累加，放量前先用样本估算。

### 判定结果必须校准与交叉验证

判定输出不是事实。全量前：

1. **校准样本**：挑 8-12 张质量两极且**本地已知**的样本先跑（历史归档类、过短内容、高复用标记），看判定是否分得开。分辨不开就改 question，不要放量。
2. **交叉验证**：用本地确定性事实校验判定方向。例：deprecated 类应几乎全部落 archive、过短内容的 reusable 均值应显著低于全体、空模板节不应拉低 reusable（若拉低了说明模型判的是模板不是内容）。不一致说明 question 或 state 有问题，回头改。
3. **置信度分层**：action/defect 置信度低的批次单独列出交人工，不自动执行。

### 精度限制写进报告

Jev 主训练语言是英文，CJK 内容准确率低于英文。中文为主的语料**绝对精度**受限，但相对排序与分类一致性经交叉验证后可用——报告里显式说明，别让读数被当成精值。长卡被截断的也要注明受影响条数。
